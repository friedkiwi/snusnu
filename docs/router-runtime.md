# Standalone Rust routing runtime

The Rust executable is the router. In automatic mode, [`--config`](router-config.md) starts LLC2, MPTN (AnyNet TCP62), and HPR/IP (Enterprise Extender) attachments and an optional concentrator connection. LLC and MPTN can route locally without Go; the HPR/IP session runtime also has a standalone path. The configured EE-to-EE datagram relay remains available as a separate mode. The WebSocket hop supports a native DLC circuit and a carrier-neutral LU session circuit, described in the [WebSocket protocol](websocket-protocol.md).

## Three separate jobs

| Job | Owns | Examples |
| --- | --- | --- |
| I/O endpoint | Local interface or socket, framing and receive/send lifecycle | Linux AF_PACKET, TCP/UDP sockets, optional WebSocket peer |
| Protocol adapter | Wire framing, discovery proof, link/session state and teardown | LLC2 XID/PIU, HPR/IP LDLC/RTP/FID5, MPTN TCP62 management and LU6.2 |
| Shared route registry | Current CP/LU ownership and next-hop selection | Local LLC, MPTN and EE attachments; upstream directory as another origin |
| Session converter | Maps a verified LU session onto its selected carrier | LLC2 PIUs, TCP62 records, HPR RTP messages, WebSocket `SessionV1` |

An endpoint is not itself a route, and an arbitrary byte string is not a common protocol. Each adapter validates its own discovery evidence, then replaces its owner snapshot in [`RouteRegistry`](../sna_router/crates/router-core/src/route_registry.rs). The registry holds a network-qualified CP or LU and the attachment to contact; it does not own the carrier's wire correlators or sockets. New sessions select one unambiguous next hop and validate its route lease before use. Each adapter owns its local timers and protocol acknowledgements. The session bridge owns the binding, failure propagation, queue limits and pressure between legs.

LLC discovery starts when a dialout guest sends XID to a local proxy MAC. The LLC adapter verifies the peer CP from XID3, tracks its attachment association and learns LU reachability from subsequent management/session evidence. A passive LLC guest that never dials out cannot be discovered by this implementation. MPTN discovery validates TCP62 management/BIND and associates learned LUs with the peer CP; confirmed shared transport loss withdraws that attachment's proof. EE discovery validates its XID3 CP and RouteSetup/BIND evidence before making a user LU reachable. Configured names are hints, not live proof. An attachment replacement or withdrawal invalidates stale route leases; duplicate identities on different attachments are withheld as ambiguous. A concentrator connection contributes its authorized directory and managed MAC bindings, and its assigned NETID limits **upstream publication**, not local route selection.

For a native LLC2 circuit, useful events are `Type1(XID|TEST, bytes)`, `Connected`, `Piu(bytes)`, `Closed` and `Reset`; commands include sending Type 1 traffic, opening/closing the link, sending a PIU and changing receive-busy state. The event identity includes local endpoint, peer MAC and SAP pair. Do not call HPR NLPs or AnyNet MPTN records `Piu` merely to fit this interface. EE's event stream must distinguish LDLC control and UI HPR NLP; AnyNet's must distinguish MPTN connect/BIND, normal/expedited data, UNBIND and keepalive.

## Route compatibility

| Ingress ↔ egress | Required route behavior | Initial status |
| --- | --- | --- |
| Native LLC2 ↔ native LLC2 | Relay Type 1 and PIU events while terminating LLC2 independently | Configured multi-peer runtime; V4R4 pass-through completed through `--config` |
| Native LLC2 ↔ MPTN | Translate one verified LU6.2 session between native PIUs and TCP62 records | V5R4 TCP62 → concentrator → V4R4 LLC2 Sign On passed on 2026-11-03; opposite direction also passed in earlier QA runs. Teardown gaps remain. |
| MPTN ↔ MPTN | Configured TCP62 session forwarding and IPv4 UDP node-pair keepalive translation | V5R4 AnyNet pass-through and live idle keepalive completed through Rust relay |
| HPR/IP ↔ HPR/IP (EE) | Preserve LDLC/HPR UDP payloads and priority ports between configured peers | Configured UDP relay completed V5R4 pass-through through separate TAPs |
| HPR/IP ↔ native HPR LAN | Possible HPR media conversion with per-leg XID/link state and both LAN SAP paths | Separate direct V5R4 captures and a typed LAN port prototype; mixed-link activation unverified |
| HPR/IP ↔ legacy LLC2 APPC | Terminate EE adjacency/RTP and translate verified LU6.2 sessions | V5R4 EE → concentrator → V4R4 LLC2 and V4R4 LLC2 → concentrator → V5R4 EE both reached remote Sign On on 2026-11-03; teardown and concurrency remain under test. |
| Native LLC2 ↔ WebSocket ↔ native LLC2 | Transport a versioned logical circuit between Rust routers; each router owns its local LLC2 state | Working V4R4 pass-through, including Go QA concentrator; multi-circuit hub has mock-server tests |

Reject unsupported or ambiguous **explicit** routes when loading configuration; automatic mode resolves from live discovery. Local route selectors differ: LLC uses endpoint/MAC/SAP, MPTN uses a validated session destination and peer association, and HPR/IP uses IP/SAP/TG link identity. MPTN correlators identify live sessions rather than static routes. Exported reachability uses network-qualified [CP or LU identities](os400-sna-names.md) without publishing those local selectors. A configured conversion must state its protocol and supported session scope.

Explicit `[[route]]` definitions remain useful for fixed pairs and constrained converters. With no explicit route, automatic mode selects from the live directory, including a concentrator hop when configured. The current HPR session path supports one EE attachment and a bounded user-session slot; it is not an arbitrary multi-peer APPN network node. A future HPR/IP/native HPR LAN adapter needs its own tested SAP and link activation. Conversion cannot be implemented by forwarding raw PIU bytes into another wire format.

## Implementation status and next protocol work

1. **Local runtime and discovery:** [`AutoLocalSessionRunner`](../sna_router/crates/snusnu-router/src/auto_runtime.rs) owns process-long LLC and TCP62 attachments. Their protocol-specific proof feeds one [`AutomaticFabric`](../sna_router/crates/snusnu-router/src/routing.rs) registry. EE uses that owner through [`HprSharedLocal`](../sna_router/crates/snusnu-router/src/hpr_shared_local.rs) and adds its verified destinations. A lost WebSocket connection withdraws upstream routes while local discovery remains available. The fixed `--lab-link` and `--local-link` modes remain available.
2. **Remote hop:** `transport-ws` and Go carry native DLC circuits and `SessionV1` LU session events. Go forwards circuit events and authorizes route references without knowing whether the endpoint is LLC, MPTN or EE. The Rust hub exports local CP/LU proof only in its concentrator-assigned NETID; managed MAC bindings are server-owned and separate from route exports.
3. **MPTN gateway:** bounded TCP/UDP 397 codecs and native LU6.2 conversion are implemented for IBM AnyNet peers. The [cross-NETID lab](cross-netid-lab.md) reached V4R4 remote Sign On from V5R4 TCP62 over two Rust routers and Go on 2026-11-03. An earlier ordinary standalone LLC2-to-MPTN config reached V5R4 Sign On. The automatic runner now leases a verified LLC dialout association for a local MPTN session, releases it after the session, and retains the discovery proof for later calls; this newer behavior has focused tests but still needs a repeat live local test. General native address selection, concurrent sessions, clean teardown and live OS/400 UDP `0x83` interoperability still need verification.
4. **EE gateway:** the automatic HPR/IP listener terminates LDLC, control/user RTP, route setup and a user LU6.2 session. V5R4 EE reached the Go embedded APING responder and V4R4 Sign On through EE → Rust → Go → Rust → LLC2 on 2026-11-03. V4R4 LLC2 also reached V5R4 remote Sign On through the reverse concentrator path at 18:23:36 UTC. The [HPR/IP gateway record](hpr-gateway.md) details the tested paths and remaining teardown and concurrency limits. The separate configured EE↔EE UDP relay has also completed a V5R4 pass-through.

The direct V4R4 trace continues from a user BIND and FMH-5 Attach to an 82-byte GDS X'12A0' record. Its header matches the 5250 startup record in [IBM-authored RFC 2877 §9](https://www.rfc-editor.org/rfc/rfc2877.html#section-9). It is application data, not an APPC Attach acknowledgment; the observed `I903` response code has no meaning assigned in that RFC. The Rust parser correlates the record for diagnostics only. A native router must forward the Attach to an actual destination LU/transaction program and let that application produce the status record.

The V5R4 lab guests completed a direct AnyNet session, a direct EE session, and an EE session through the Rust relay. The V4R4 LLC2 pass-through remains the native DLC interoperability baseline.

Protocol background: [RFC 2353, APPN/HPR in IP Networks](https://www.rfc-editor.org/rfc/rfc2353.html); [IBM-authored TCP62 Internet-Draft](https://datatracker.ietf.org/doc/html/draft-ietf-tn3270e-tcp62-00); [IBM System i EE configuration](https://www.ibm.com/support/pages/configuring-ee-enterprise-extender-between-two-ibm-system-i-systems). The EE-to-HPR-LAN media-adapter possibility is an inference pending captures, not an interoperability claim.
