# Managed virtual MACs for LLC targets

An OS/400 LAN APPC controller that initiates a connection sends its first XID to the `ADPTADR` remote adapter address. Snusnu can present a stable **virtual target MAC** on that guest's local LAN and map the MAC/SAP to a network-qualified CP route. The target may actually be behind another LLC link, AnyNet, or Enterprise Extender; the remote IP peer does not need an Ethernet MAC. An answering controller can also learn an incoming address through automatic controller creation, so not every SNA endpoint requires a configured virtual MAC. See IBM's [LAN, Frame-Relay and ATM Support guide](https://public.dhe.ibm.com/systems/power/docs/systemi/v5r4/en_US/sc415404.pdf), chapter 2.

## Allocation boundary

The concentrator automatically assigns one stable virtual LLC target MAC when a CP is first advertised. LUs hosted by that CP use its link address and do not receive one MAC each. MAC is a local data-link alias, not the SNA identity of a CP/LU. An MPTN/TCP62 peer has an IP endpoint and needs no Ethernet MAC of its own; the allocated CP MAC is used only where an LLC guest addresses that CP.

Assignments live in a durable server-owned address-book table, keyed by the owning user and qualified CP name with a unique MAC constraint. A CP may move between Rust routers without changing the address configured in OS/400. A live route advertisement or `route_id` is transient and does not own the lease. If the same CP is advertised from several routers, routing preference and authorization decide the active path; the address book does not allocate a new MAC for each advertisement. Users and routers cannot select, disable, override or retire these addresses.

A possible pool is `02:53:4E:00:00:01` through `02:53:4E:FF:FF:FF`, allocating a unique 24-bit suffix transactionally. The first octet `02` is locally administered and unicast. Call `02:53:4E` a **snusnu local MAC prefix**, not an IEEE-assigned OUI: it is unique only within this concentrator's administrative domain, and an unrelated deployment could use the same prefix. [IEEE's EUI/OUI guidelines](https://standards-support.ieee.org/hc/en-us/articles/4888705676564-Guidelines-for-Use-of-Extended-Unique-Identifier-EUI-Organizationally-Unique-Identifier-OUI-and-Company-ID-CID) and [RFC 9542](https://www.rfc-editor.org/rfc/rfc9542.html) distinguish local addresses from registered OUIs.

Offline or withdrawn routes retain their assignment. Deleting an address-book CP retires and tombstones the MAC; do not automatically reuse it after a timer. An old OS/400 `ADPTADR` can remain configured indefinitely and could otherwise connect to a different CP. The pool has about 16.7 million values, so permanent retirement is practical. If reclamation becomes necessary, require an explicit administrative action after old controller configurations are cleared.

The global directory shows the assigned MAC and SAP `04` for both a CP and each LU that uses its hosting CP, while retaining the hosting-CP relationship. Administrators have a read-only operational allocation view with the twelve-hex-digit `ADPTADR` form and advertising routers. Ordinary users have no MAC-management page. The user still configures the directory address in OS/400; publishing it does not modify the guest controller.

Go pushes the CP-to-virtual-MAC binding only to authorized LLC-facing routers, alongside or after the server-stamped reachability snapshot. The Rust publisher's `RouteSnapshot` stays MAC-free; a client cannot claim a managed address merely by advertising a CP. The downstream schema carries these bindings in the server-owned `ManagedCpBindingSnapshot` message. Each `[[llc]]` keeps its required `guest_mac`; a concentrator-backed route normally omits `[[route]] proxy_mac` and waits for the managed binding before accepting or transmitting LLC frames. For an LLC-to-LLC route, each port uses the opposite peer's `guest_mac` by default. Other LLC-facing routes require a route-owned `proxy_mac` when no managed binding exists.

The Rust router accepts server-issued assignments only over its WebSocket connection, validates local/unicast bits, managed prefix and local-LAN uniqueness, and maps the assigned MAC to the corresponding target CP. An explicitly configured managed-prefix `[[route]] proxy_mac` on a concentrator-backed route is provisional and can be replaced while LLC is disconnected. A standalone LLC proxy address is never replaced by a server binding. Check the prefix **only for managed virtual addresses**: guest hardware MACs and standalone local LLC routes can legitimately differ. Prefix checks are configuration validation, not concentrator authentication; a rogue server could invent the same prefix. Authenticate a WSS server using TLS certificate/hostname validation, with a private trust root or pin if that deployment requires one. [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html) specifies TLS service-identity checks.

The first two-V4R4 WebSocket interoperability run can keep the already working guest `ADPTADR` values `02:00:35:27:23:01` and `02:00:35:27:23:02`. Managed aliases are an additional address-book feature and need not block that test.
